# ระบบรับงาน AI โรงไม้110

## สถานะที่ตรวจพบ 21 ต.ค. 2569

แอปเดิมเก็บคำสั่งในกระดานโดยรอรอบ ChatGPT ยังไม่มีบริการ AI หรือ worker เชื่อมอยู่
โค้ดฉบับนี้เพิ่มคิวถาวร ตัวประมวลผล และหน้าผลงาน แต่การเผยแพร่โค้ดเพียงอย่างเดียวไม่เปิดบริการ AI 24 ชั่วโมง
ต้องเชื่อมบัญชี AI และนำตัวรับงานไปรันในบริการที่ทำงานต่อเนื่องก่อน จึงทดสอบงานจริงจนอ่านผลงานกลับได้

## เส้นทางงาน

1. ทุกแผนกส่งคำสั่งไป `/api/ai/queue` ด้วย UUID เดิมเมื่อส่งซ้ำ บันทึก task และ job ใน D1 ชุดเดียวกัน
2. เมื่อมีบริการ AI และ heartbeat ของ worker ภายใน 90 วินาที แอปส่งคำขอ background ทันที
3. สถานะ provider `queued` ยังเป็นรอเริ่ม; `in_progress` จึงเป็นกำลังทำ; `completed` พร้อม JSON ที่ผ่าน validation จึงส่งรอตรวจ
4. Worker อิสระอ่านคิวทุก 2 วินาที ทำได้ไม่เกิน 4 งานต่อรอบ มี lease 45 วินาทีป้องกันรับซ้ำ
5. ผลงาน งานรอตรวจ ประวัติฝ่าย และเรื่องรออนุมัติบันทึกใน batch เดียว ไม่รับรองงานภายนอก และไม่เปลี่ยนรอตรวจเป็นเสร็จ
6. การแก้โจทย์หรือปิดงานระหว่างประมวลผลจะไม่ถูกเขียนทับ ผลที่ได้ยังเก็บอยู่ใน job เพื่อให้ตรวจด้วย `/api/ai/jobs?id=UUID`

ไม่มีการส่งอีเมล โทร เผยแพร่ ซื้อโฆษณา แก้สัญญา หรือสั่งงานหน้างานจาก engine นี้
โมเดลมีเพียงเครื่องมืออ่านเว็บเมื่อเปิดใช้; งานภายนอกเป็นเรื่องรออนุมัติและต้องให้คนลงมือ
การอนุมัติในกระดานไม่สั่งให้ engine ไปทำกิจกรรมภายนอกโดยอัตโนมัติ

## การตั้งค่าก่อนเปิดจริง

ตั้งผ่านระบบจัดการ environment ของ Site เท่านั้น:

| ชื่อ | ความหมาย |
| --- | --- |
| `OPENAI_API_KEY` | Secret จากบัญชี AI ที่มีสิทธิ์และงบสำหรับแอป |
| `OPENAI_MODEL` | โมเดลที่บัญชีใช้งานได้ รองรับ background Responses และ structured JSON |
| `AI_WORKER_SECRET` | Secret สุ่มอย่างน้อย 32 ตัวอักษร ใช้ให้ตรงกับ worker |
| `AI_WEB_SEARCH_ENABLED` | `true` เพื่ออนุญาตอ่านเว็บ; ค่าเริ่มต้นปิด |

ใช้ native Sites tool ตั้ง secrets และเผยแพร่ saved version เพื่อให้ environment revision มีผล
ห้ามใส่ secret ในแชต source browser หรือ hosting manifest

รัน `scripts/ai-worker.mjs` บน host ที่เปิดตลอดเวลา ตั้งค่าตาม `.env.ai-worker.example`:
`RM110_SITE_BEARER` ต้องเป็น Site service credential ที่รองรับ ไม่ใช่ cookie ของผู้ใช้
สิทธิ์นี้ไม่ให้สิทธิ์อ่าน Gmail หรือแอปอื่น ต้องไม่ขยายผู้ชม Site เพื่อให้ worker เข้าถึงได้
Node receiver ไม่ต้องถือ OpenAI key โดยตรง; key อยู่ฝั่ง Site

ตัวอย่างตรวจการเชื่อมต่อบน host หลังตั้งค่า environment:

```sh
node scripts/ai-worker.mjs --once
docker compose -f compose.ai-worker.yaml up -d --build
```

ไฟล์ `.env.ai-worker` อยู่บน host และต้องไม่เข้า Git; ดูแล restart และความพร้อมของ host ตามระบบปฏิบัติการ
Sites ในงานนี้มีสัญญา D1/HTTP แต่ไม่ได้ประกาศคิวหรือ cron binding สำหรับ runtime จึงไม่อาศัย scheduled handler ที่ไม่มีตัวเรียก
ไม่มีการสร้าง automation ChatGPT ซ้ำเพื่ออ้างว่าเป็น immediate worker

## เงื่อนไขลองใหม่

- รับไม่เกิน 30 คำสั่งใหม่ใน 24 ชั่วโมง ไม่รวมการอ่านสถานะคำขอเดิม
- ตอบ 429 ชั่วคราวหรือ 5xx: ลองสร้างคำขอไม่เกิน 3 ครั้งรวมครั้งแรก เว้น 30 วินาที แล้ว 120 วินาที
- เมื่อมี response ID: อ่านคำขอเดิมอีกครั้งเมื่ออ่านสถานะขัดข้อง ไม่ส่ง POST ซ้ำ
- หากส่งแล้วไม่ได้รับ ID/การยืนยัน: หยุดและแจ้งผลไม่แน่นอน ไม่ลองซ้ำอัตโนมัติซึ่งอาจเกิดค่าใช้จ่ายซ้ำ
- สิทธิ์ผิด โควตาหมด output ไม่สมบูรณ์ หรือโจทย์เปลี่ยน: ติดขัดพร้อมเหตุผล ไม่มีผลงานสำเร็จปลอม
- งานที่ติดขัดทั่วไปเริ่มใหม่จากแอปได้หลังตรวจสาเหตุ งานผลไม่แน่นอน/โจทย์เปลี่ยนต้องตรวจคำขอเดิมก่อน
- Background Responses ใช้ `store:false` แต่ provider เก็บข้อมูลชั่วคราวเพื่ออ่านผล จึงต้องมี worker ต่อเนื่อง ไม่ทิ้งรอผลเป็นชั่วโมง

## การยืนยันก่อนประกาศว่าเปิดใช้งาน

1. หน้า “ระบบและวิธีทำงาน” แสดงบริการ AI พร้อมและ heartbeat ปัจจุบัน
2. ส่งคำสั่งทดสอบจากแอปแล้วปิดหน้าเว็บ ตรวจว่า job ไป `review` พร้อม task result และประวัติฝ่ายตรงกัน
3. ตรวจกรณีส่งซ้ำ worker สองตัว retry และหยุด/เริ่ม worker ว่าไม่สร้างผลงานหรือคำขอซ้ำ
4. ทดสอบคำสั่งติดต่อ/ใช้เงิน: ต้องมีร่างและ pending approval; ไม่มีการส่งหรือใช้เงินจริง
5. ทดลองโดยใช้บัญชี AI ที่อนุมัติงบแล้ว การทดสอบจำลองไม่ใช่หลักฐานว่าบริการจริงพร้อม
